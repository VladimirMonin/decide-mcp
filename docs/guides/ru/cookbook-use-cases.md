# 06. Базовые кейсы использования и паттерны из кукбуков разработчиков

Документ объединяет проверенные паттерны из официальной документации **TypeSafe AI (Jev)**, **Google (`gemini-decision-1`)**, **OpenAI Decisions API (`gpt-6-luna`)** и **Microsoft (`Microsoft-Decision-1.1`)** и показывает, как они реализуются через 2 рабочих инструмента `decide_run` и `decide_query`.

---

## Часть I. Фундаментальные паттерны вендоров

### Паттерн 1. Трёхзонный гейтинг (TypeSafe AI / Jev)
**Откуда:** базовый гайд TypeSafe AI — запрещается принимать критичные решения по одному жёсткому порогу `0.5`.
**Механика:**
* `prob >= 0.90` — **зелёная зона** (действие или классификация принимается автоматически).
* `prob <= 0.10` — **красная зона** (надёжно отбрасывается).
* `0.10 < prob < 0.90` — **серая зона** (передаётся на разбор большой рассуждающей модели System Two или человеку).
**Применение в `decide-mcp`:** после `decide_run` агент через `decide_query` (`action: "filter"`) забирает на ручной/System-Two разбор только элементы из серой зоны (или выше верхнего порога), экономя 80–90% контекста.
**Оговорка безопасности (Prompt Injection):** для финансовых операций, удаления данных или прав доступа даже `prob >= 0.99` от одной decision-модели недостаточно — из-за однопроходной архитектуры злоумышленный текст во входе может сдвинуть вероятности. В таких ветках decision-модель используется только как маршрутизатор на проверку.

### Паттерн 2. Последовательное сужение / Воронка Coarse-to-Fine (TypeSafe AI + Google)
**Откуда:** документация TypeSafe (`sequential narrowing`) и гайды Google по упаковке до 1 000 вопросов в один запрос `gemini-decision-1`.
**Механика:** вместо того чтобы прогонять 500–1 000 объектов через 15 сложных вопросов (дорого и долго), матрицу раскладывают в каскад:
1. **Широкий скрининг (`N × 1`):** 1 дешёвый `score` (или `bool`) на каждый элемент в сжатом виде (`skeleton`).
2. **Глубокий разбор (`K × M`):** только топ-`K` финалистов (15–150 шт.) получают полную проекцию данных и 5–12 ортогональных вопросов.
3. **Сравнительный шортлист (опционально):** когда осталось `<= 20` кандидатов (ниже порога деградации `choice` ~50 опций), одним финальным `choice` можно напрямую сравнить финалистов и выбрать топ-1.

### Паттерн 3. Композитный скоринг вместо одного размытого вопроса (Composite Scoring)
**Откуда:** общая рекомендация по проектированию рубрик System One API.
**Проблема:** вопрос «Насколько критичен этот баг/файл?» плохо калибруется — модель смешивает разные критерии в непредсказуемых пропорциях.
**Решение:** в одном батче задаются 3–4 конкретных атомарных вопроса (например, `affects_prod`, `has_workaround`, `data_loss_risk`, `missing_tests`), а итоговый рейтинг считается формулой с весами на стороне клиента (или фильтрами `decide_query`). Веса и приоритеты можно менять мгновенно без переписывания рубрики и повторных вызовов API.

### Паттерн 4. Спекулятивный веер (Speculative Fan-Out)
**Откуда:** паттерн обхода изоляции вопросов внутри одного запроса.
**Проблема:** вопросы в одном батче не видят ответов друг друга. Если вопрос Б логически нужен только при `да` на вопрос А, наивный подход требует двух последовательных HTTP-запросов.
**Решение:** если задержка второго сетевого раунда (~1 сек через прокси) дороже лишних 100–200 входных токенов, выгоднее положить в первый же вызов `decide_run` вопросы для всех веток сразу, а в `decide_query` отфильтровать неактуальные ветки по значению вопроса А.

### Паттерн 5. Вынос справочника в `state` + якорь `other` (Google `gemini-decision-1`)
**Откуда:** документация Google по матрицам `N × M` без контекстного кэширования.
**Механика:**
* Все длинные определения правил кладутся **один раз** в `rubric.guide` (ядро вставляет их в шапку `state`).
* В каждом `choice` запасная категория называется строго `other`, чтобы при алфавитной сортировке ключей внутри Gemini она уходила в конец и не перетягивала вероятности.

### Паттерн 6. Скользящее окно по переходам `state -> tool_call` (Microsoft `Microsoft-Decision-1.1`)
**Откуда:** штатный паттерн Microsoft (включая бенчмарк When2Call) под компактное окно 32K токенов.
**Механика:** вместо загрузки всей длинной сессии целиком берётся целевой шаг вызова инструмента и узкое окно соседних сообщений (`context_window: 2`), а в `choice` допускается явный вариант отказа (`cannot tell` / `other`), если из локального окна причина не видна.

### Паттерн 7. Кэширование префикса длинной сессии (OpenAI `gpt-6-luna`) *(задел на прямой адаптер v2)*
**Откуда:** спецификация OpenAI `/v1/decisions` (`prompt_cache_key`, `prompt_cache_breakpoint`, TTL 30 мин) и нативные `function_call` / `function_call_output`.
**Механика:** один раз фиксируется длинный контекст (до 1.05M токенов), после чего поверх него прогоняются последовательные волны до 400 вопросов со скидкой на чтение кэша. В MVP через `/v1/systemone` используется огромное окно `luna` для длинных модулей, а явный `prompt_cache_key` подключается в v2-адаптере `OpenAIDecisionsProvider`.

### Паттерн 8. Страховка `box` через Companion Noul и тайлинг (TypeSafe AI / Jev 1.14) *(справочно для v2)*
**Откуда:** гайд TypeSafe по визуальной локализации (отложено за рамки текстового MVP, но важно для будущих проверок скриншотов UI):
1. **Companion Noul:** `box` всегда возвращает координаты, даже если объекта нет — в тот же запрос обязательно ставится `bool` (`noul`) «Есть ли объект X?».
2. **Множественность:** рядом ставится `choice` (`none`, `one`, `several`); при `several` кадр режется на сетку.
3. **Двухпроходный тайлинг:** мелкие детали (20–30 px на 4K) сначала локализуются по сектору через `choice`, затем `box` вызывается на кропе тайла; если `confidence < 0.6`, к рамке добавляется отступ `PAD = 0.05`.

## Часть II. Базовые прикладные кейсы для `decide-mcp`

### Кейс 1. Аудит кодовой базы, логирования и тестов
**Задача:** быстро прочесать 50–300 файлов проекта перед релизом или рефакторингом, найти проглоченные ошибки, слепые места в логах и критичную логику без тестов.
* **Модель:** `jev` (дёшево и точно по коду) или `gemini` (если файлов очень много).
* **Источник:** `glob` (`"src/**/*.{ts,py}"`).
* **Рубрика:** `rubrics/code_review_and_logs.json` (паттерн Composite Scoring: `swallowed_errors`, `missing_critical_tests`, `risky_implementation`, `log_quality` `score 0..3`, `main_debt` `choice`).
* **Рабочий цикл агента:**
  1. `decide_run` с `dry_run: true` — проверить, что не зацепили лишние папки и оценить токены.
  2. `decide_run` (`dry_run: false`) — получить сводку по `main_debt` и топ-15 проблемных файлов.
  3. `decide_query` (`action: "filter"`) — отдельно выгрузить все файлы, где `swallowed_errors >= 0.80` или `log_quality <= 1.0`.
  4. Агент открывает только отобранные 8–10 файлов и предлагает точечные исправления.

### Кейс 2. Быстрый триаж прикладных логов (Log Triage)
**Задача:** разобрать дамп из 500–2 000 строк/записей ошибок после падения на проде, отделить одноразовый шум от критичных сбоев и разложить их по подсистемам.
* **Модель:** `gemini` (до 1 000 записей за 1 вызов).
* **Источник:** `jsonl` (или `file` с `mode: "lines"`).
* **Рубрика:** `rubrics/logs_triage.json` (`severity` `score 0..3`, `is_actionable` `bool`, `is_transient_noise` `bool`, `subsystem` `choice` с `other`).
* **Рабочий цикл агента:**
  1. `decide_run` прогоняет весь лог (при наличии «грязных» строк срабатывает автоделение батча пополам на `HTTP 400`).
  2. `decide_query` (`action: "aggregate"`) показывает, какая подсистема дала больше всего критичных ошибок.
  3. `decide_query` (`action: "inspect"`) с `context_window: 3` вытаскивает топ-5 инцидентов с соседними строками лога до и после падения.

### Кейс 3. Четырёхэтапная воронка анализа сессий агента (1 000+ шагов)
**Задача:** найти системные дыры в инструкциях и описаниях инструментов по длинным логам агента (включая многословный `reasoning` моделей DeepSeek / Qwen).
* **Этап 1 (Скрининг скелета):** `decide_run` на `gemini`, `source: jsonl (projection: "skeleton", prefilter_tags: true)`, `rubric: rubrics/agent_funnel_stage1.json`. Отсекаем ~85% нормы.
* **Этап 2 (Диагностика с полным reasoning):** `decide_run` на `gemini` или `jev`, `source: from_run (where: problem_score >= 1.5, context_window: 2, projection: "full")`, `rubric: rubrics/agent_funnel_stage2.json`.
* **Этап 3 (Первопричины):** `decide_run` на `jev`, `source: from_run` (подтверждённые сбои Этапа 2), `rubric: rubrics/agent_funnel_stage3.json` (в `guide` кладётся оглавление системного промпта и список тулов).
* **Этап 4 (Правки):** основной агент через `decide_query` (`aggregate` + `inspect`) получает 3–5 примеров на каждую топовую причину и правит промпт/docstrings.

### Кейс 4. Проверка правильности выбора инструментов агентом (When2Call)
**Задача:** проверить, не дёргает ли агент лишние инструменты и не передаёт ли кривые аргументы на коротких эпизодах.
* **Модель:** `ms` (`microsoft/microsoft-decision-1` — сильна именно на When2Call, узкое окно 32K здесь идеально).
* **Источник:** `from_run` с `context_window: 1` (только предыдущий запрос + сам вызов тула + ответ тула).
* **Рубрика:** inline-рубрика от агента с `bool` (`tool_needed`, `args_valid`) и `choice` (`tool_fit`: `exact_match`, `wrong_tool`, `redundant_call`, `cannot_tell`).

### Кейс 5. Калибровка порогов и сравнение моделей (A/B-прогон)
**Задача:** понять, какая из 4 моделей (`jev`, `gemini`, `ms`, `luna`) точнее ловит нужный класс багов на твоих данных и какие пороги для неё выставить.
* **Механика:**
  1. Берётся контрольная выборка из 20–30 характерных элементов (`text` или `jsonl` с `limit: 30`).
  2. Запускаются два `decide_run` с одинаковой рубрикой на разных моделях (например, `jev` и `gemini`).
  3. Вызывается `decide_query` (`action: "compare"`, `run_id`, `compare_run_id`).
  4. Видны точные расхождения по каждому элементу — на их основе выбираются рабочие пороги для автоматических воронок.

### Кейс 6. Прогон произвольной разовой проверки («анализ чего угодно на лету»)
**Задача:** проверить нестандартную гипотезу, под которую нет готового пресета (например: «найди все SQL-миграции с риском длинной блокировки таблиц» или «проверь 200 учебных вопросов на двусмысленность формулировки»).
* **Механика:** агент запрашивает `decide_models` (если нужно уточнить лимиты), прямо в аргументе `rubric` вызова `decide_run` собирает inline-JSON из 2–4 примитивов по правилам из [rubrics-and-funnels.md](rubrics-and-funnels.md), запускает `dry_run: true`, затем боевой прогон и разбирает топ через `decide_query`. Код инструмента при этом менять не нужно.
