## 0. Назначение, границы и словарь

Документ задаёт проверочный набор для позиционного скана текстов, которые уходят в GitHub:
кода, документации, рубрик, fixtures и отчётов. Скан ищет **только две категории** — API-ключи
и ФИО. Телефоны, адреса, паспортные данные, cookies и банковские реквизиты в набор не входят
и в рубрику не добавляются.

Границы подготовки: файлы проекта только читались, git не трогался, платных вызовов `decide_run`
не было (0 ₽). Настоящие ключи и настоящее ФИО владельца в документ не подставлены: все значения
синтетические и помечены. Реальный `.env` не открывался — сверялся только формат `.env.example`.

**Вердикты.** Каждый пример получает ровно один:

| Вердикт | Значение | Что делает скан |
|---|---|---|
| `LEAK` | Действительный секрет или ФИО реального человека | Блокирует публикацию |
| `WARN` | Фингерпринт, логин, имя без пометки «пример» | Не блокирует, уходит человеку |
| `CLEAN` | Имя переменной, шаблон, плейсхолдер, регулярка, хэш, пример | В находки не попадает |

**Почему набор нужен именно такой.** Существующий локальный санитайзер уже знает узкий список
сигнатур (`src/cli/bench-check.ts:128-136`, `src/cli/funnel-check.ts:158-165`): `pza_`, `sk-`
(в том числе случайно `sk-or-v1-`), `ghp_`, `AKIA`, `xox[baprs]-`, `Bearer`, присваивание
`POLZA|OPENROUTER_API_KEY`. Он не покрывает Google `AIza`, Telegram bot token, JWT,
`github_pat_`, query-строки без узнаваемого префикса, экранированные и обходные формы.
Категории ФИО в нём нет вовсе. Этот набор закрывает обе дыры
и отдельно фиксирует ложные срабатывания, на которых наивный regex ломается.

## 1. Категория A. API-ключи

Общая сигнатура категории: префикс провайдера + тело достаточной длины, либо транспортная форма
(`Authorization`, `api_key=`), либо высокая энтропия рядом с ключевым словом. Плейсхолдер
отличается от ключа не «похожестью», а длиной, маркером и контекстом.

### A1. Polza AI: префикс `pza_`

**Сигнатура:** `\bpza_[A-Za-z0-9]{20,}\b`. Порог 20 символов после префикса отделяет ключ от
тестовой заглушки. **Где встречается:** `.env`, вывод smoke, тело ошибки шлюза, README-пример
секции `mcpServers`.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `POLZA_API_KEY=pza_SYNTH7Q2mZx4Kp9Rt3Vb8Nc1Ld` | Присваивание, 26 символов после префикса, высокая энтропия |
| `LEAK` | `"apiKey": "pza_SYNTH7Q2mZx4Kp9Rt3Vb8Nc1Ld"` | JSON-конфигурация MCP-клиента |
| `CLEAN` | `POLZA_API_KEY=your_polza_api_key_here` | Плейсхолдер `.env.example:8` |
| `CLEAN` | `Authorization: Bearer ${POLZA_API_KEY}` | Ссылка на переменную, не значение |
| `CLEAN` | `pza_test_key` | `src/core/config.test.ts:11`, 8 символов после префикса, маркер `test` |
| `WARN` | `pza_SYNT` в тексте ошибки | Обрезанный фингерпринт: не ключ, но подтверждает, что ключ был |

**Ловушка:** `pza_super_secret` в `src/core/config.test.ts:73` — это литерал в тесте, который
проверяет, что сводка конфигурации **не** содержит ключ. 12 символов после префикса, ниже порога → `CLEAN`.
Строка `assert.equal(summary.includes("pza_super_secret"), false)` тоже `CLEAN`: это утверждение
об отсутствии, а не утечка.

### A2. OpenRouter: `sk-or-v1-`

**Сигнатура:** `\bsk-or-v1-[A-Za-z0-9]{32,}\b`, старый формат — `\bsk-or-[A-Za-z0-9]{32,}\b`.
**Где встречается:** `.env`, README, `decide_models`-вывод, фикстуры ответов.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `OPENROUTER_API_KEY=sk-or-v1-SYNTH000000000000000000000000000000000000` | Валидная длина и префикс |
| `LEAK` | `sk-or-SYNTH000000000000000000000000000000` | Старый формат без `v1`; смена формата не делает ключ безопасным |
| `CLEAN` | `sk-or-test` | `src/core/config.test.ts:41`, тело `test` — 4 символа |
| `CLEAN` | `sk-or-v1-…` | Многоточие вместо тела |
| `WARN` | `sk-or-v1-…f3a2` | Последние 4 символа — фингерпринт для ротации, публиковать нельзя |

### A3. OpenAI / Anthropic: `sk-`

**Сигнатура:** `\bsk-(?:ant-[a-z0-9]+-)?[A-Za-z0-9_-]{20,}`. Граница слова обязательна, иначе
ловятся `disk-usage` и `risk-assessment`.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `sk-SYNTH000000000000000000000000` | 29 символов после префикса |
| `LEAK` | `sk-ant-api03-SYNTH0000000000000000` | Формат Anthropic |
| `CLEAN` | `docs/disk-usage-report.md` | `\b` перед `s` не срабатывает: `disk` продолжается |
| `CLEAN` | `risk-assessment`, `task-sketch` | Те же ложные срабатывания на дефисе |
| `CLEAN` | `sk-***`, `sk-<your-key>` | Маска и шаблон |
| `WARN` | `sk-…9f2c` | Маскированный фингерпринт |

### A4. GitHub: `ghp_`, `github_pat_`

**Сигнатура:** `\bgh[pousr]_[A-Za-z0-9]{36}\b`, `\bgithub_pat_[A-Za-z0-9_]{50,}\b`.
**Где встречается:** конфиги CI, документация деплоя, `.mcp.json`.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `ghp_SYNTH0000000000000000000000000000000` | 36 символов после префикса |
| `LEAK` | `github_pat_11SYNTH0000000000000000000000000000000000000000000000000000` | Fine-grained token |
| `CLEAN` | `GITHUB_TOKEN` | Имя переменной окружения без значения |
| `CLEAN` | `ghp_xxx`, `ghp_…` | Заглушка и маска |
| `WARN` | `ghp_…c1d2` | Фингерпринт |

### A5. AWS: `AKIA` / `ASIA`

**Сигнатура:** `\b(?:AKIA|ASIA)[A-Z0-9]{16}\b`.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `AKIASYNTH00000000000` | `AKIA` + 16 символов |
| `LEAK` | `aws_secret_access_key = SYNTHwJalrXUtnFEMI/K7MDENG` | Секретная часть пары; ключевое слово рядом |
| `CLEAN` | `AKIAIOSFODNN7EXAMPLE` | Канонический пример из документации AWS; allowlist по точному значению |
| `CLEAN` | `akia...` строчными, `AKIA` без тела | Не тот регистр, обрезано |
| `WARN` | `AKIA…` с многоточием | Маска |

**Ловушка:** `AKIAIOSFODNN7EXAMPLE` проходят не все сканеры: он формально валиден по алфавиту
и длине. Это единственный случай, где нужен allowlist по **точному** значению, а не по префиксу.
Любой другой `AKIA…` той же формы остаётся `LEAK`.

### A6. Google: `AIza`

**Сигнатура:** `\bAIza[A-Za-z0-9_-]{35}\b`. Один формат у Maps, Gemini и Cloud — категория одна.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `AIzaSYNTH000000000000000000000000000000` | 35 символов после `AIza` |
| `LEAK` | `?key=AIzaSYNTH000000000000000000000000000000` | Ключ в query-строке |
| `CLEAN` | `AIza` без тела, `AIzaSy…` | Обрезано |
| `WARN` | 36 символов вместо 35 (лишний символ) | Почти-ключ: проверить руками |

### A7. Slack: `xox[baprs]-`

**Сигнатура:** `\bxox[baprs]-[A-Za-z0-9-]{10,}\b`.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `xoxb-SYNTH-000000000000-000000000000-abcdefghijklmnop` | Полный bot token |
| `LEAK` | `xoxp-SYNTH-000000000000-000000000000-abcdefghijklmnop` | User token |
| `CLEAN` | `xoxb-`, `xox` в тексте | Нет тела |
| `WARN` | `xoxb-…` | Маска |

### A8. Telegram bot token

**Сигнатура:** `\b\d{8,10}:[A-Za-z0-9_-]{35}\b`; в URL — `api\.telegram\.org/bot<token>/`.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `123456789:AAHSYNTH000000000000000000000000000` | 9 цифр + 35 символов |
| `LEAK` | `https://api.telegram.org/bot123456789:AAHSYNTH000000000000000000000000000/getMe` | Токен в пути URL |
| `CLEAN` | `12:34:56`, `1:1000000000` | Время и соотношение, не токен |
| `CLEAN` | `123456789:` без тела | Обрезано |
| `CLEAN` | `12345678-1234-1234-1234-123456789012` | UUID, цифры и дефисы, двоеточия нет |
| `WARN` | `bot123456789:AAH…` | Маска в URL |

### A9. JWT

**Сигнатура:** `eyJ[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]{8,}`.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJTWU5USCJ9.SYNTH0000000000000000000000000000` | Три сегмента, валидный заголовок |
| `LEAK` | `Cookie: session=eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJTWU5USCJ9.SYNTH0000` | Токен в заголовке |
| `CLEAN` | `data:image/png;base64,iVBORw0KGgoAAAANSUhEUg` | Base64 картинки начинается с `iVBOR`, не с `eyJ` |
| `CLEAN` | `eyJhbGci` в тексте про структуру JWT | Фрагмент заголовка без полезной нагрузки |
| `WARN` | JWT с `"alg":"none"` | Подпись не секрет, но в payload могут быть ФИО и id — передать в категорию B9 |

### A10. Заголовок `Authorization` во всех синтаксисах

**Сигнатура:** `(?i)(?:proxy-)?authorization\s*[:=]\s*(?:bearer|basic|token)\s+\S{6,}` плюс
`(?i)x-api-key\s*[:=]\s*\S{8,}`.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `Authorization: Bearer pza_SYNTH7Q2mZx4Kp9Rt3Vb8Nc1Ld` | Классическая форма |
| `LEAK` | `"Authorization": "Bearer sk-or-v1-SYNTH000000000000000000000000000000000000"` | JSON, ключ в кавычках |
| `LEAK` | `curl -H "Authorization: Bearer sk-SYNTH000000000000000000000000" https://…` | Команда из истории терминала |
| `LEAK` | `authorization: bearer pza_SYNTH7Q2mZx4Kp9Rt3Vb8Nc1Ld` | Нижний регистр не отменяет секрет |
| `LEAK` | `Proxy-Authorization: Basic U1lOVEg6cGFzcw==` | Basic-креденшл: base64 от `user:pass` |
| `CLEAN` | `Authorization: Bearer ${POLZA_API_KEY}` | `src/core/providers/systemone.ts:492` — шаблон |
| `CLEAN` | `Authorization: Bearer <token>`, `Bearer [REDACTED]` | Шаблон и маркер редакции |
| `CLEAN` | `Авторизация: Authorization: Bearer ${POLZA_API_KEY}` | `docs/architecture/providers-and-models.md:46`: ячейка таблицы, а не значение |

### A14. Ключ в тексте ошибки, лога и артефакта

Это не отдельная сигнатура, а путь утечки, который уже существует в коде:

1. шлюз отвечает `401`, в `error.message` или `error.metadata.raw` приходит сам ключ;
2. `classifyHttpError` кладёт `message` и `rawDetail` в текст `ProviderError` (`src/core/providers/systemone.ts:103-111`), сырое тело — в `body` (`:120-143`);
3. `engine.ts:641` переносит `failure.message` в `error_summary`, `store.ts:382` пишет его в SQLite;
4. `mcp.ts:92` печатает первые 500 символов сообщения в stderr;
5. `engine.ts:197-199` (`previewOf`) сохраняет первые 300 символов элемента в `items.preview`, а `top_items[].preview` возвращается агенту;
6. транскрипт агента с этим текстом становится fixture и уходит в репозиторий.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `HTTP 401: Incorrect API key provided: pza_SYNTH7Q2mZx4Kp9Rt3Vb8Nc1Ld` | Шлюз вернул ключ в теле ошибки |
| `LEAK` | `preview: "Authorization: Bearer sk-SYNTH000000000000000000000000"` | Строка источника попала в preview |
| `CLEAN` | `Не задан POLZA_API_KEY. Добавьте ключ в .env.` | Только имя переменной |
| `CLEAN` | `[REDACTED_API_KEY]`, `Bearer [REDACTED]` | Маркеры `src/cli/bench-check.ts:129-135` |
| `WARN` | `pza_SYNT…` в `error_summary` | Маска провайдера: ключ был, значение скрыто |

**Вывод для скана:** проверять не только исходники, но и `error_summary`, `items.preview`,
`top_items[].preview` в выгрузке SQLite и тексты отчётов `docs/verification/`.

### A15. Самореференция: регулярки, имена переменных, поисковые шаблоны

Самая частая ложная тревога: сканер находит собственный шаблон.

| Ожидание | Пример | Почему |
|---|---|---|
| `CLEAN` | `[/(pza_[A-Za-z0-9]+)/g, "[REDACTED_API_KEY]"]` | Класс символов, а не значение (`bench-check.ts:129`) |
| `CLEAN` | `\b(?:POLZA|OPENROUTER)_API_KEY\s*=\s*\S+` | Определение сигнатуры (`funnel-check.ts:165`) |
| `CLEAN` | `grep -ril "authorization\|bearer\|POLZA_API_KEY" fixtures/probes/` | Поиск по ключевым словам (`fixtures/bench/bench-session.jsonl:80`), значений нет |
| `CLEAN` | `SECRET_PATTERNS`, `apiKey: config.provider.apiKey` | Имя поля и ссылка на объект |
| `LEAK` | `const KEY = "pza_SYNTH7Q2mZx4Kp9Rt3Vb8Nc1Ld"` | Конкретное значение в литерале |

**Правило различения:** регулярка содержит `[`, `\`, `(`, `|`, `*` и не содержит конкретного
тела; имя переменной не имеет значения; присваивание конкретной строки — имеет.

### A16. Обходные формы

Сканер обязан нормализовать текст **до** сопоставления, иначе эти четыре формы проходят мимо
(та же ошибка, что с экранированными путями в `bench-check.ts`, функция `normalizePathEscapes`).

| Ожидание | Пример | Нормализация |
|---|---|---|
| `LEAK` | `рzа_SYNTH7Q2mZx4Kp9Rt3Vb8Nc1Ld` (кириллические `р`, `а`) | NFKC + карта конфузабельных символов |
| `LEAK` | `pza_SYNT\u200B0000000000000000000000` | Удалить zero-width (`U+200B`, `U+FEFF`, `U+00AD`) |
| `LEAK` | `pza\_SYNTH7Q2mZx4Kp9Rt3Vb8Nc1Ld` и `pza\\_SYNTH…` | Снять экранирование `\_`, `\\` |
| `LEAK` | `POLZA_API_KEY=pza_SYNTH\` + перенос + `7Q2mZx4Kp9Rt3Vb8Nc1Ld` | Склеить продолжение строки (`\` в конце, отступ) |
| `LEAK` | `"apiKey":` на одной строке, значение на следующей | Окно из 3 строк, а не одна строка |
| `WARN` | `pza_SYNT` после переноса без обратного слэша | Обрыв без продолжения: похоже на маску |

**Цена решения:** позиционный скан по одной строке слеп к переносам. Либо источник режется
окнами по 3 строки с перекрытием, либо локальный препроцессор склеивает продолжения до нарезки.

## 2. Категория B. ФИО

Общая сигнатура: два-три русских слова с заглавной буквы, где среднее входит в список имён,
последнее оканчивается на `-ович/-евич/-овна/-евна`, а первое — на фамильный суффикс. Одного
совпадения мало: решают падеж, контекст и признак «пример/реальное».

### B1. Полное ФИО подряд, именительный падеж

**Сигнатура:** `\b[А-ЯЁ][а-яё-]{2,}(?:ов|ев|ёв|ин|ын|ский|цкий|ко|ук|юк|ян)\s+[А-ЯЁ][а-яё]{2,}\s+[А-ЯЁ][а-яё]{3,}(?:ович|евич|ьевич|овна|евна|ьевна|ична)\b`.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `Иванов Иван Иванович` в `retrospectives/`, без пометки | Триплет в документе, который уходит в GitHub |
| `LEAK` | `Ответственный: Петрова Анна Сергеевна` | ФИО в служебном поле отчёта |
| `CLEAN` | `Иванов Иван Иванович (заглушка)` в примере рубрики | Явная пометка в той же строке |
| `WARN` | `Пётр I`, `Иван Грозный` | Исторические лица: публичны, но однофамилец возможен |
| `WARN` | `Иван Иванович` без фамилии | Два токена: имени и отчества мало для блокировки |

### B2. Обратный порядок: имя, отчество, фамилия

**Сигнатура:** те же три токена в порядке `Имя Отчество Фамилия`.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `Иван Иванович Иванов` | Полный триплет, порядок не спасает |
| `LEAK` | `Anna Sergeevna Petrova` | Латиница, см. B4 |
| `CLEAN` | `Иван да Марья` | Фольклорная пара, не человек |
| `WARN` | `Иван Иванович` | Нет фамилии: имени и отчества мало для блокировки |
| `WARN` | `Иван Иванович, директор` | Похоже на подпись, но фамилия отсутствует |

### B3. Фамилия с инициалами

**Сигнатура:** `\b[А-ЯЁ][а-яё-]{2,}\s+[А-ЯЁ]\.\s?[А-ЯЁ]\.` и обратный порядок `[А-ЯЁ]\.\s?[А-ЯЁ]\.\s+[А-ЯЁ][а-яё-]{2,}`.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `Иванов И.И.`, `И.И. Иванов`, `Иванов И. И.` | Фамилия + инициалы: достаточно для идентификации в проекте |
| `CLEAN` | `и.о. директора`, `и.п.`, `т.е.`, `п.п.` | Аббревиатуры строчными, не инициалы |
| `CLEAN` | `г. Москва`, `д. 5`, `стр. 12` | Сокращения адреса |
| `WARN` | `И.И.` без фамилии | Слишком слабо: блокировать нельзя |
| `WARN` | `Иванов И. И. М.: Наука, 2020` | Библиографическая ссылка: публичные данные, но если это публикация владельца — это его личность |

**Ловушка:** `и.о.` (исполняющий обязанности) — самая частая ложная тревога на инициалы.
Регистр и точка после каждой буквы обязательны для `LEAK`.

### B4. Латиница и транслитерация

**Сигнатура:** `\b[A-Z][a-z]{2,}(?:ova|eva|ina|skaya|tskaya|ov|ev|in|sky|tsky|ko|uk|yan)\s+[A-Z][a-z]{2,}\s+[A-Z][a-z]{2,}(?:ovich|evich|ovna|evna)\b`.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `Ivanov Ivan Ivanovich`, `Petrova Anna Sergeevna` | Транслит полного ФИО |
| `LEAK` | `Petrov P.S.` | Фамилия + инициалы латиницей |
| `CLEAN` | `John Doe`, `Jane Doe`, `Test User` | Канонические английские заглушки |
| `CLEAN` | `John Smith` | Заглушка из документации |
| `WARN` | `Ivan Ivanov` | Два токена, оба частые: вероятный транслит реального человека |

Латиница опаснее кириллицы: `Ivanov` не ловится русским списком имён, а в метаданных пакета,
лицензии и почтовых адресах имя обычно записано именно так.

### B5. Падежные формы в переписке и тексте

**Сигнатура:** основы из B1 + падежные окончания (`-у`, `-ым`, `-ой`, `-е`, `-а`).

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `Передайте Иванову Ивану Сергеевичу` | Дательный падеж полного ФИО |
| `LEAK` | `от Петровой Анны Викторовны` | Родительный падеж |
| `CLEAN` | `Ивановская область`, `Ивановский район` | Топоним-прилагательное |
| `CLEAN` | `улица Иванова`, `проспект Петровский` | Топоним |
| `CLEAN` | `завод «Ивановский»`, `ООО «Ромашка»` | Организация |
| `WARN` | `с Ивановым` | Только фамилия в творительном: слабо, но проверить |

**Правило:** сначала стем, потом падежное окончание, затем исключение по словам-маркерам
топонима и организации (`область`, `район`, `улица`, `проспект`, `шоссе`, `завод`, `ООО`, `АО`,
`ИП`, `ТЦ`). `ИП Иванов Иван Иванович` — исключение из исключения: это всё равно человек.

### B6. Имя в email

**Сигнатура:** локальная часть адреса, разложенная по `[._-]`, содержит пару «имя + фамилия»
или транслит фамилии.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `ivan.ivanov@gmail.com` | Реальный почтовый домен + имя и фамилия |
| `LEAK` | `i.petrov@yandex.ru`, `petrova_av@corp.ru` | Имя/фамилия с инициалами, корпоративный домен |
| `CLEAN` | `user@example.com`, `admin@example.com` | Ролевые адреса |
| `CLEAN` | `support@example.com`, `noreply@example.com`, `test@example.com` | Служебные ящики |
| `CLEAN` | `ivan.ivanov@example.com` | Зарезервированный домен `example.com` + заглушки |
| `WARN` | `ivanov@example.com` | Только фамилия; домен-заглушка спасает, но локальная часть — реальная фамилия |

**Ловушка:** домен `example.com` — сильный признак примера, но не индульгенция. Если та же
локальная часть встречается где-то с реальным доменом, пример становится копией настоящего
адреса → `LEAK` по совокупности.

### B7. Авторство в метаданных и коде

**Сигнатура:** `(?i)(?:@author|author|автор|copyright|co-authored-by|maintainer)\s*[:=]?\s*.{0,40}` + ФИО или транслит.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `@author Иван Петров` | JSDoc-шапка файла |
| `LEAK` | `"author": "Ivan Petrov <ivan.petrov@gmail.com>"` | `package.json` |
| `LEAK` | `Co-authored-by: Ivan Petrov <ivan.petrov@gmail.com>` | Трейлер коммита в тексте отчёта |
| `LEAK` | `Copyright (c) 2026 Иван Петров` | `LICENSE` |
| `CLEAN` | `@author decide-mcp contributors` | Коллективное авторство |
| `CLEAN` | `"author": "decide-mcp"`, `Copyright (c) 2026 decide-mcp` | Организация |
| `WARN` | `user.name = ivanov` | Логин без имени: не ФИО, но идентифицирует |

### B8. ФИО и логин в путях

**Сигнатура:** `[A-Za-z]:[\\/]Users[\\/]([^\\/\s]+)` и `/home/([^/\s]+)`, плюс кириллица в имени файла.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `C:/Users/ivanov/work/report.md` | Логин человека в домашнем пути |
| `LEAK` | `docs/Иванов_Иван_отчёт.md` | ФИО в имени файла |
| `LEAK` | `/home/petrov/decide-core` | Логин на Linux |
| `CLEAN` | `C:/Users/User/...` | Стандартный профиль Windows; в рабочем дереве таких путей два |
| `CLEAN` | `C:/Users/Public/...`, `%USERPROFILE%`, `~/`, `<HOME_PATH>` | Системные и маскированные формы |
| `WARN` | `C:/Users/ipetrov/...` | Логин, производный от имени и фамилии |

### B9. ФИО в цитате переписки и в reasoning

**Сигнатура:** имя рядом с глаголом речи (`сказал`, `написал`, `попросил`, `подтвердил`,
`says`, `asked`, `wrote`) или внутри кавычек.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `«…» — написал Иван Петров в переписке` | Прямая цитата частной переписки |
| `LEAK` | `reasoning: "Иван попросил переделать отчёт"` | Имя в цепочке рассуждений агента |
| `CLEAN` | `— Привет, меня зовут Иван. — Это пример.` | Вымышленный диалог с пометкой |
| `CLEAN` | `[фрагмент удалён по приватности]` | Маркер редакции, как в `fixtures/bench/bench-session.jsonl:80` |
| `WARN` | `Иван сказал, что…` без фамилии | Слабая форма, но в своих документах это почти всегда владелец |

Проект уже умеет это для reasoning: `bench-check.ts` заменяет поле целиком маркером
`[фрагмент удалён по приватности]`, если видит `QUOTE_MARKERS`. Тот же приём применим к B9
на этапе публикации, но скан обязан найти такие строки **до** редакции.

### B10. Инициалы без фамилии

**Сигнатура:** `\b[А-ЯЁ]\.\s?[А-ЯЁ]\.` в блоке подписи, в шапке письма, в поле «Исполнитель».

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `С уважением, И.П.` | Блок подписи: инициалы однозначно указывают на человека |
| `LEAK` | `Исполнитель: И. П.` | Служебное поле |
| `CLEAN` | `и.о.`, `и.п.`, `т.д.`, `п.н.` | Аббревиатуры, не инициалы |
| `CLEAN` | `I.P.` в техническом тексте (`IP-адрес`) | Латиница без точек-разделителей |
| `WARN` | `И. П.` в заголовке таблицы | Контекста не хватает |

**Правило:** одиночные инициалы никогда не блокируют публикацию. `LEAK` — только при наличии
подписного контекста (`С уважением`, `Исполнитель`, `Подпись`, `Author`).

### B11. Кластер персональных данных

**Сигнатура:** ФИО + email, ФИО + логин, ФИО + телефон в одном абзаце.

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `Иванов Иван Иванович, ivanov@gmail.com` | Связка имени и контакта на реальном домене |
| `LEAK` | `Петрова Анна Сергеевна (petrova_av@corp.ru)` | То же в скобках |
| `CLEAN` | `Иванов Иван Иванович (заглушка)` | Один триплет с пометкой |
| `WARN` | `Иванов Иван Иванович, Москва` | Имя и город: не контакт, но сужает круг |

Телефоны и адреса — третья категория, в этот скан не входят. Кластер фиксируется по связке
«ФИО + email/логин»; телефон в примере используется только как иллюстрация и в рубрику
не добавляется.

### B12. Пример в рубрике против реального ФИО

Главный кейс категории: одна и та же строка может быть и безопасной, и утечкой.

| Ожидание | Пример | Почему |
|---|---|---|
| `CLEAN` | `"responsible": "Иванов Иван Иванович"` в `docs/guides/ru/rubrics-and-funnels.md` с пометкой «пример» рядом | Демонстрационные данные, помечены |
| `LEAK` | `"responsible": "Иванов Иван Иванович"` в `retrospectives/2026-11-23-….md` без пометки | Рабочий отчёт, имя не объяснено |
| `LEAK` | Имя совпадает с `package.json` → `author`, git-идентичностью или подписью в `retrospectives/` | Совпадение с реальной личностью превращает пример в утечку |
| `WARN` | Имя встречается один раз, пометки нет, в identity-источниках его нет | Недостаточно данных: решает человек |

**Правило двух источников.** Имя считается реальным, если оно (а) помечено как пример — тогда
`CLEAN`; (б) встречается в identity-источниках (`package.json`, `LICENSE`, `.mailmap`,
`docs/verification/`, `retrospectives/`, git-конфигурация) — тогда `LEAK`; (в) иначе — `WARN`.
Файловый маркер «здесь примеры» не отменяет проверку: пометка должна стоять рядом со строкой.

### B13. Ложные срабатывания: организации, топонимы, исторические лица

| Ожидание | Пример | Почему |
|---|---|---|
| `LEAK` | `ИП Иванов Иван Иванович` | Индивидуальный предприниматель — физическое лицо |
| `CLEAN` | `ООО «Ромашка»`, `АО «Вектор»` | Юридическое лицо |
| `CLEAN` | `Ивановский район`, `Петровский сквер` | Топоним |
| `CLEAN` | `Пётр Великий`, `Иван Фёдоров` | Исторические фигуры, публичные данные |
| `WARN` | `Иванов и партнёры` | Фирма названа по фамилии: возможен однофамилец владельца |

## 3. Как отличить реальное от примера

### 3.1. Маркеры значения

| Маркер | Где допустим | Что означает |
|---|---|---|
| `SYNTH` в теле ключа | Этот файл и сгенерированные фикстуры | Синтетика; настоящий ключ такого не содержит |
| `deadbeef`, серия нулей | Hex-примеры, этот файл | Заполнитель вместо случайного hex |
| base64 от строки с `SYNTH` | Этот файл | Синтетический base64 и JWT-payload |
| `your_*_here`, `_here` | `.env.example`, README | Плейсхолдер |
| `${VAR}`, `<token>`, `{{var}}` | Документация, код | Ссылка на переменную |
| `***`, `…`, `xxx`, `[REDACTED_*]` | Отчёты, логи | Маска; значения нет |
| `stub`, `test`, `dummy`, `fake`, `example` | Тесты, фикстуры | Заглушка |
| `(заглушка)`, `пример`, `example` рядом с ФИО | Документация | Демонстрационные данные |

### 3.2. Список имён-заглушек

Разрешённый набор для примеров: фамилии `Иванов`, `Петров`, `Сидоров`, `Кузнецов`, `Смирнов`;
имена `Иван`, `Пётр`, `Анна`, `Мария`, `Алексей`; отчества `Иванович`, `Петрович`, `Сергеевич`,
`Ивановна`, `Сергеевна`, `Викторовна`. Всё, что вне списка и без пометки «пример», идёт в `WARN`
или `LEAK` по контексту. Список узкий намеренно: широкий набор имён превращает сканер в
генератор ложных тревог.

### 3.3. Проверка по identity-источникам

Имя реально, если встречается хотя бы в одном из: `package.json` (`author`, `contributors`),
git-идентичность автора коммита, поля «исполнитель» в `docs/verification/`, подпись в
`retrospectives/`. `LICENSE` и `.mailmap` в проекте пока отсутствуют, но при появлении входят
в тот же список. Совпадение с ним — `LEAK` независимо от того, как строка выглядит.

### 3.4. Нормализация до сопоставления

Порядок обязателен и одинаков для ключей и ФИО:

1. Unicode NFKC и карта конфузабельных символов (кириллические `р`, `а`, `е`, `о`, `с`);
2. удаление zero-width (`U+200B`, `U+FEFF`, `U+00AD`);
3. снятие экранирования `\_`, `\\`, `\/` (git-bash вывод удваивает слэши);
4. URL-декодирование (`%5F` → `_`);
5. склейка продолжений строки (`\` в конце, отступ у следующей);
6. только потом — регулярка и окно контекста.

### 3.5. Три независимых прохода

Одна регулярка не доказывает ни находку, ни чистоту — это уже подтвердилось на экранированных
путях. Минимальный набор:

1. **Регулярки** — сигнатуры из разделов A и B, с порогами длины.
2. **Контекст** — ключевое слово в пределах 40 символов, признак примера в той же строке,
   падеж и слова-маркеры топонима.
3. **Decision-модель** — `decide_run` по спорным и по случайной выборке «чистых» строк.

Расхождение проходов — сигнал `WARN`, а не повод выбрать удобный ответ.

### 3.6. Маскирование в отчётах

| Категория | В публичном артефакте | В приватном отчёте |
|---|---|---|
| API-ключ | `<REDACTED:pza_:len26>` — без символов значения | Префикс + последние 4 для ротации |
| ФИО | `И***в И.И.` | Полное, если это нужно для решения |

Правило простое: публикация не содержит ни одного символа секрета; приватный отчёт содержит
минимум, достаточный для ротации ключа или опознания человека.

## 4. Порядок позиционного скана

### 4.1. Что сканируется

Только то, что уходит в GitHub: файлы рабочего дерева вне `.git`, `node_modules`, `dist`,
`.decide-mcp`, `artifacts`, `*.log`. `.env` в скан **не** попадает: проверяется лишь его
наличие и факт игнора. Отдельно проверяются выгрузки SQLite (`error_summary`, `items.preview`,
`top_items[].preview`) и `fixtures/**`, потому что именно они переносят текст провайдера
и транскрипта в репозиторий.

### 4.2. Гранулярность и позиции

Позиция — это `путь:строка`. Штатный `file` + `mode: "lines"` её сохраняет: `item_id` =
`путь#L105` (`src/core/sources.ts:263-267`). А `glob` даёт item = целый файл с `item_id` = путь
(`src/core/sources.ts:331`), без номера строки. Поэтому для массового обхода источник режется
локально, 0 ₽:

```jsonl
{"id":"docs/architecture/contracts.md#L46","content":"| Авторизация | Authorization: Bearer ${POLZA_API_KEY} |"}
{"id":"src/core/config.ts#L86","content":"    const keyName = providerName === \"polza\" ? \"POLZA_API_KEY\" : \"OPENROUTER_API_KEY\";"}
```

`id` восстанавливает позицию без обратного поиска (тот же формат `путь#Lстрока`, что у `file`), а `content` — одна строка. Переносы
значения обрабатываются окном из 3 строк (A16) до нарезки, а не после.

### 4.3. Черновик рубрики

Две оси, ровно по категориям задания. Формат — внутренний `Rubric` из
`docs/architecture/contracts.md`; `bool` переводится в `noul` внутри провайдера.


### 4.4. Дешёвый префильтр

До платных вызовов, 0 ₽:

1. отбросить строки без ни одного из маркеров `pza_`, `sk-`, `ghp_`, `AKIA`, `AIza`, `xox`,
   `eyJ`, `bearer`, `api_key`, `token`, `secret`, `users/`, `@`, `author`, `copyright`;
2. оставить кандидатов по сигнатурам A1–A16 и B1–B13;
3. добавить 10 % случайной выборки отброшенных строк — контроль ложных пропусков;
4. прогнать `decide_run` только по этому набору.

### 4.5. Приёмка

| Метрика | Порог |
|---|---|
| Полнота на `LEAK` | 100 %: ни один положительный пример не пропущен |
| Блокирующие ложные срабатывания на `CLEAN` | 0 |
| `WARN` | Разрешены, перечислены в отчёте с причиной |
| Позиция | Совпадает с ожидаемой строкой; при двух находках в строке — два интервала |
| Повтор | Краевые кейсы (`WARN`) прогоняются дважды; расхождение моделей — ручное решение |

Первый прогон — `dry_run` и `--catalog-only`; живой — минимальным набором строк и с пометкой
`[PAID]` (шлюз, модель, `usage.cost_rub`). В этой подготовке платных вызовов не было: 0 ₽.

### 4.6. Самореференция

Этот файл содержит положительные примеры и сам попадает под скан. Правило: файл-фикстура
с маркером `scanner-fixture` не блокируется **только** на значениях из своей грамматики
(`SYNTH`, `deadbeef` и нули в hex, base64 от `SYNTH`, имена из §3.2, домен `example.com`). Любое другое значение в нём — обычная
находка. Иначе сканер либо блокирует сам себя, либо получает слепую зону, в которую можно
случайно вставить настоящий ключ.

## 5. Что этим набором не проверяется

- **Реальная энтропия настоящего ключа.** Синтетические значения не воспроизводят распределение
  символов боевого ключа. Компенсация: публичные примеры вендоров (`AKIAIOSFODNN7EXAMPLE`) и
  ручная проверка одного настоящего ключа в приватном канале.
- **Git-история.** `.git` в этой подготовке не читался. Ключ, удалённый из HEAD, остаётся
  в истории и требует отдельной проверки перед публикацией.
- **Телефоны, адреса, cookies, банковские данные.** Третья и последующие категории; в рубрику
  не добавлены, чтобы не размывать пороги двух осей.
- **Содержимое `.env`.** Файл секретен и не сканировался; проверялся только формат
  `.env.example` и факт игнора в `.gitignore`.
