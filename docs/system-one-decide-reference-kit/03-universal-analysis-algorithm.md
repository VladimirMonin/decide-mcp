# 03. Универсальный алгоритм проектирования анализа

Этот алгоритм не привязан к конкретному проекту. Он описывает воспроизводимый инженерный процесс: как из размытой задачи «хочу проверить X на большом массиве данных» собрать точный, измеримый и предсказуемый пайплайн на базе System One + System Two.

---

## Общая схема конвейера

```text
[Шаг 0: Гейт применимости]
        │  (подходит System One?)
        ▼
[Шаг 1: Проба формата (Probe-Before-Code)] ──► 0 ₽, реальные байты
        │
        ▼
[Шаг 2: Нарезка единицы анализа (Карточки)] ──► локальный скрипт, 0 ₽
        │
        ▼
[Шаг 3: Проектирование рубрики и осей]      ──► guide + атомарные примитивы
        │
        ▼
[Шаг 4: Калибровка весов (Контрольная 4-ка)]──► ~1–3 ₽, compare 2 моделей
        │
        ▼
[Шаг 5: Трёхслойная воронка]
   ├─ Слой 0: Бесплатные эвристики / теги (0 ₽)
   ├─ Слой 1: Массовый скрининг по скелету (gemini / ms)
   └─ Слой 2: Глубокая диагностика с окном контекста (from_run, jev / gemini)
        │
        ▼
[Шаг 6: Синтез System Two по SQLite]        ──► aggregate + inspect (топ 5–15)
```

---

## Шаг 0. Гейт применимости: нужен ли вообще System One?

Перед написанием кода ответьте на три вопроса по порядку:

1. **Можно ли проверить детерминированным скриптом (регулярки, парсер, `git log`, AST, сравнение списков)?**
   - *Да* → **пишите скрипт (0 ₽, 100% точность).** Не тратьте модели на подсчёт коммитов, поиск путей `C:\Users\` или проверку валидности JSON.
2. **Объём маленький (до 20–30 коротких элементов) или задача чисто творческая/субъективная («почему пользователю не понравится этот тон»)?**
   - *Да* → **отдайте сразу одной рассуждающей LLM (System Two).** Воронка здесь только добавит возни, а на субъективных предсказаниях System One может дать точность хуже монетки (46% в тесте предсказания «вмешается ли пользователь»).
3. **Данных много (десятки/сотни файлов, шагов, логов, карточек), критерии можно свести к проверяемым признакам, либо нужен регулярный независимый аудит с метриками в SQLite?**
   - *Да* → **строим связку System One → System Two.**

---

## Шаг 1. Проба формата (`Probe-Before-Code`)

**Железное правило:** никогда не пишите парсер и не запускайте платные вызовы по описанию в README или по памяти.
- Откройте 2–3 реальных сырых файла/записи.
- Убедитесь, что нужные вам данные **вообще существуют в логе** (пример из нашего опыта: в описании дампера говорилось «селектор `custom` — блоки памяти», а проба на реальном `session.jsonl` показала, что `pi-memory` вставляет память в рантайме и не пишет её в лог — проба остановила пустой прогон за 0 ₽).
- Проверьте реальные ключи связки между файлами (например, `runId`, `parentSession`, `call_id`).
- Не парсите сгенерированный Markdown обратно в JSONL регулярками — читайте исходный формат (`jsonl`, `json`, исходный код, сырой лог) напрямую.

## Шаг 2. Выбор единицы анализа (карточки)

**80% качества анализа решается не выбором модели, а правильной нарезкой карточки.** Модель видит только то, что вы положили в `state`.

| Тип задачи | Неудачная единица | Правильная единица (карточка) |
| :--- | :--- | :--- |
| **Проверка делегирования** | Отдельный шаг в общем логе | **Тройка:** `постановка оркестратора` + `итог воркера` + `вердикт ревьюера` |
| **Проверка следования ТЗ** | Только итоговый код/текст | **Пара:** `конкретное требование из ТЗ` + `соответствующий фрагмент результата` |
| **Аудит подмешивания памяти / RAG** | Весь блок `<memory>` из 15 записей целиком | **Атомарная связка:** `запрос` + **`1 конкретная запись`** + `фрагмент реакции агента` |
| **Аудит сессии на сбои** | Весь 10-МБ лог целиком | **Два среза:** сначала сжатый `skeleton` каждого шага, затем подозрительный шаг + **окно ±2 соседних шага** (`from_run`) |
| **Проверка текста/сценария** | Одно предложение без контекста | **Смысловой блок/сцена** + `краткий бриф (цель, аудитория, запреты)` |
| **Проверка объекта на фото** | Слишком большой снимок с мелкой деталью | **Двухшаговый кроп:** вся картинка → грубый `Box`/тайл → увеличенный кроп |

**Правило обрезки:** не режьте текст карточки без нужды (например, на 2 200 символов, когда окно `gemini` 262K). Урезанный хвост чаще всего содержит как раз критерии приёмки или замечания ревьюера.

**Дайджест размышлений вместо обрезки по краям.** Первые и последние `200` символов `thinking` прячут главное: разворот чаще всего в середине. Собирайте начало (~`1 200` символов) + конец (~`1 200` символов) + до `3` окон по ±`300` символов вокруг маркеров разворота: `Wait`, `Actually`, `Но`, `Подождите`, «Но нет», `стоп`, «нет, не так».

**Считайте реальную сборку, а не расчётную оценку.** SQL-оценка `--estimate` пугала `26 тыс.` символов, а реальный сборщик (`inject-probe`) на том же блоке показал `7 654–8 000` символов без обрезки: оценка считает потенциально доступное, а не то, что действительно попадает в блок. Перед выводом «не влезает» соберите один реальный блок.

## Шаг 3. Проектирование рубрики и осей

1. **Вынесите контекст и определения в `guide` (один раз).** В самих вопросах оставляйте только чёткую проверку.
2. **Один вопрос — один атомарный факт.** Разбивайте составные вопросы («нарушен ли процесс A, B или C?») на отдельные `noul` и собирайте итог в коде (`Composite scoring`).
3. **Разводите пользу и вред на разные оси.** Не делайте шкалу от «вредно» до «полезно» — одна и та же запись или шаг могут быть и полезными по сути, и создающими трение по форме. Держите отдельно `helped` (`score 0..2`) и `caused_friction` (`score 0..2`).
4. **Обязательно добавляйте ось положительного рычага (`positive_leverage`).** Без неё любая ретроспектива превращается в фабрику запретов, которые потом конфликтуют между собой. Фиксируйте, какие решения сэкономили время или предотвратили сбой.
5. **Обязательная заглушка `other` в каждом `choice`.** Всегда описывайте, когда модель должна выбрать `other`, и не используйте имя `none_of_the_above`.
6. **Используйте `Speculative fan-out`:** если 4–8 вопросов логически относятся к одной карточке, отправляйте их **одним запросом**, а не последовательными вызовами.
7. **Делайте `dry_run: true` перед платным прогоном:** проверьте число карточек, число батчей, оценку токенов и отсутствие переполнения лимитов шлюза (`256` для `gemini`, `200` для `luna`).

## Шаг 4. Калибровка «весов» до боевого прогона

Никогда не верьте красивым цифрам на новом пайплайне, пока не проверили чувствительность рубрики. Тестировать весы на одних «хороших» данных бессмысленно — вы не узнаете, способна ли модель вообще нажать «брак».

### Метод контрольной четвёрки (8–12 карточек, ~1–3 ₽)
Возьмите 2–3 реальных кейса и соберите для каждого 4 варианта:

| Тип контрольной карточки | Содержимое | Что обязана ответить живая рубрика |
| :--- | :--- | :--- |
| **1. Чистый эталон** | Полное ТЗ / хороший материал + чистый результат | Высокое качество, `defect = other` |
| **2. Явный брак** | Карикатурно пустое ТЗ / очевидная ошибка | Низкий балл, точное попадание в нужный дефект |
| **3. «Реалистичная ловушка»** *(главный тест)* | Длинный, аккуратный, «красивый» текст/ТЗ, откуда **незаметно вырезано одно важное условие** + конфликт именно по нему | Модель не должна купиться на красивую форму; если купилась — замените общую оценку на прямой `noul` сверки («было ли условие явно указано?») |
| **4. Инверсия вины** | То же длинное ТЗ, где условие **явно есть** + тот же конфликт | Причина должна переключиться с «слабой постановки» на «ошибку исполнителя» |

### Три тонкости, без которых контрольная четвёрка обманывает
- **Случайная выборка почти целиком нормальная.** В пилоте здоровыми оказались `14` из `15` записей — такая выборка проверяет только «модель не шумит», но не «модель ловит брак». Синтетические контроли обязательны.
- **Нельзя проверять исправленную рубрику на тех же карточках, по которым чинил.** Нужна свежая порция, которую модель не видела: одна и та же рубрика дала `89,5%` на старой выборке и `70,0%` на `10` свежих карточках — разрыв показывает, насколько знакомые карточки льстят результату.
- **Ровные числа — не результат.** На массовом прогоне `gemini` выдал подозрительно симметричное `22/22/22` по трём типам дефектов: это признак склонности модели выравнивать классы. Такие числа — список кандидатов для проверки глазами, а не приговор.

### Парная сверка (`compare`) и настройка гейтинга
- Прогоните 20–30 реальных карточек на паре моделей (например, `gemini` + `jev`).
- Смотрите не на абсолютные числа (калибровки у моделей разные), а на **контраст внутри каждой модели** и на **карточки, где модели разошлись**.
- Настройте **трёхзонный гейтинг**:
  - обе модели уверены в норме → автопропуск;
  - обе уверены в проблеме → автофлаг в отчёт;
  - серая зона (`0.30..0.70` по `noul`, низкий `confidence` по `score`, или спор между `jev` и `gemini`) → обязательный просмотр System Two или человека.

## Шаг 5. Трёхслойная воронка для больших объёмов

Когда элементов сотни или тысячи (логи, длинные сессии, большой репозиторий):

1. **Слой 0 — Бесплатный предфильтр (`prefilter_tags`, 0 ₽):** локальный скрипт помечает явные маркеры (повторы инструментов, HTTP 4xx/5xx, длинные `thinking`, моменты `compaction`, брошенные `branch`, большие диффы).
2. **Слой 1 — Массовый скрининг (`skeleton`):** по сжатому представлению каждого элемента запускается 1–2 быстрых вопроса (`problem_score` или `needs_deep_check` `noul` + классификатор фазы `choice`).
   - Модель: **`gemini`** (11,72 ₽, окно 262K — оптимально для длинных последовательностей) или **`ms`** (4,92 ₽ — для очень коротких строк логов).
   - Отсекается 80–85% рутины.
3. **Слой 2 — Целевая диагностика (`from_run` + окно контекста):** только для прошедших порог 10–15% подтягивается полный текст + соседние элементы (`context_window: 2`), и вешается полная диагностическая рубрика (4–6 атомарных `noul` + `severity` + `root_cause`).
   - Модель: **`jev`** (для точного судейства коротких/средних окон) или **`gemini`** (если окна > 32K, чтобы не терять элементы).

---

## Шаг 6. Финальный синтез System Two строго по сводкам

Все ответы System One сохраняются в локальной базе **SQLite** (`runs`, `items`, `answers`). Финальная рассуждающая модель (System Two) **не читает сырые мегабайты**:
1. Получает агрегированную статистику (`aggregate`): распределение фаз, доли сбоев, рейтинги самых проблемных сущностей.
2. Забирает точечные доказательства (`inspect`): 5–15 карточек с максимальным `severity` / `step_waste`, спорные случаи из `compare` и топ-3 карточки по `positive_leverage`.
3. Формулирует человеческие выводы: **почему** это произошло, **что именно** поменять в коде/инструкциях/процессе и **что сохранить** из удачного.
